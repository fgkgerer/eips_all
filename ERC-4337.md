# ERC-4337: Account Abstraction via Entry Point（账户抽象）

## 基本信息

| 属性       | 值                                                            |
| ---------- | ------------------------------------------------------------- |
| 编号       | ERC-4337 / EIP-4337                                           |
| 标题       | Account Abstraction via Entry Point Contract                  |
| 状态       | Final                                                         |
| 类型       | Standards Track                                               |
| 分类       | ERC                                                           |
| 作者       | Vitalik Buterin, Yoav Weiss, Dror Tirosh, Shahaf Nacson, Alex Forshtat, Kristof Gazso, Tjaden Hess |
| 创建日期   | 2021-09-28                                                    |
| 配合标准   | EIP-712（签名格式参考）, ERC-1271（理念来源）, EIP-7702（互补配合） |

## 概述

ERC-4337 是**不改变以太坊共识层的账户抽象方案**。它引入了一个独立的交易内存池（UserOperation mempool）和 EntryPoint 合约，让用户通过**智能合约账户**（而非 EOA）发起交易。账户可以自定义签名验证逻辑、支付 Gas 的方式、以及交易执行逻辑——简而言之，将账户的执行权交给用户代码。

## 核心动机

### EOA 的局限性

传统的 EOA（外部账户）存在诸多限制：

| 问题                    | 说明                                                 |
| ----------------------- | ---------------------------------------------------- |
| **只能用 ETH 付 Gas**   | 新用户必须先获取 ETH 才能交互（巨大的入门门槛）       |
| **只能用 ECDSA 签名**   | 无法使用 Passkey、BLS、社交恢复等更安全的方案        |
| **私钥丢失 = 资产丢失** | 没有恢复机制                                           |
| **只能单笔交易**        | 无法批量操作（approve + swap 必须两笔交易）           |
| **无支出限额**          | 私钥泄露即资产全部损失                                 |

### ERC-4337 的解决方案

ERC-4337 让用户使用**智能账户（Smart Account）**——一个由用户控制的智能合约——来发起操作。智能账户可以：

- 用任意 ERC-20 代币甚至由第三方代付 Gas
- 使用 Passkey、硬件钱包、手机生物识别等任意签名方案
- 设置社交恢复、监护人机制
- 支持批量交易（一次签名执行多步操作）
- 设置支出限额、时间锁等风控策略

## 技术规范

### 整体架构

```
┌─────────┐     ┌──────────┐     ┌───────────┐     ┌──────────┐
│  用户    │     │ Bundler  │     │EntryPoint │     │  Smart   │
│(签名者)  │     │ (打包者)  │     │ (入口点)   │     │ Account  │
└────┬────┘     └────┬─────┘     └─────┬─────┘     └────┬─────┘
     │               │                │                 │
     │ 1. 签名       │                │                 │
     │  UserOp       │                │                 │
     │──────────────>│                │                 │
     │               │ 2. 打包多笔   │                 │
     │               │  UserOp → tx  │                 │
     │               │──────────────>│                 │
     │               │                │ 3. 验证 UserOp │
     │               │                │────────────────>│
     │               │                │   validateUserOp│
     │               │                │<────────────────│
     │               │                │                 │
     │               │                │ 4. 执行 UserOp │
     │               │                │────────────────>│
     │               │                │   callData      │
     │               │                │<────────────────│
```

### UserOperation 数据结构

```solidity
struct UserOperation {
    address sender;              // 智能账户地址
    uint256 nonce;               // 防重放 nonce
    bytes initCode;              // 首次使用时部署账户的代码
    bytes callData;              // 账户要执行的 calldata
    uint256 callGasLimit;        // 执行阶段的 Gas 上限
    uint256 verificationGasLimit;// 验证阶段的 Gas 上限
    uint256 preVerificationGas;  // Bundler 的固定 Gas 开销
    uint256 maxFeePerGas;        // 类似 EIP-1559 的 Gas 费用
    uint256 maxPriorityFeePerGas;
    bytes paymasterAndData;      // Paymaster 地址 + 数据（代付 Gas）
    bytes signature;             // 用户对该 UserOp 的签名
}
```

### EntryPoint 合约核心逻辑

```solidity
contract EntryPoint {
    function handleOps(
        UserOperation[] calldata ops,
        address payable beneficiary // Bundler 收款地址
    ) public {
        for (uint256 i = 0; i < ops.length; i++) {
            UserOperation calldata op = ops[i];

            // 1. 验证阶段：调用账户的 validateUserOp
            _validatePrepayment(op, userOpHash(op));

            // 2. 执行阶段：调用账户执行 callData
            _executeUserOp(op, userOpHash(op));
        }
        // 补偿 Bundler 的 Gas 费用
    }
}
```

### 智能账户必须实现的接口

```solidity
interface IAccount {
    /// @notice 验证 UserOperation 签名，成功后 EntryPoint 报销 Gas
    function validateUserOp(
        UserOperation calldata userOp,
        bytes32 userOpHash,
        uint256 missingAccountFunds
    ) external returns (uint256 validationData);
}
```

### Paymaster 代付 Gas

Paymaster 是**第三方支付 Gas 的合约**。例如，DApp 可以为用户支付 Gas 以降低门槛：

```solidity
interface IPaymaster {
    function validatePaymasterUserOp(
        UserOperation calldata userOp,
        bytes32 userOpHash,
        uint256 maxCost
    ) external returns (bytes memory context, uint256 validationData);

    function postOp(
        PostOpMode mode,
        bytes calldata context,
        uint256 actualGasCost
    ) external;
}
```

Paymaster 在 `validatePaymasterUserOp` 中决定是否为某 UserOp 付 Gas：

- **Verifying Paymaster**：检查用户签名即可代付
- **ERC-20 Paymaster**：接受用户在 callData 中指定的 ERC-20 代币作为 Gas 支付
- **Sponsored Paymaster**：DApp 赞助特定操作的 Gas

### 关键设计约束

| 约束                       | 原因                                                        |
| -------------------------- | ----------------------------------------------------------- |
| 验证阶段禁止区块相关 opcode（`TIMESTAMP`、`NUMBER`、`GASLIMIT`、`BASEFEE` 等）| 防止 Bundler 操纵区块环境来拒绝或篡改有效 UserOp              |
| 验证阶段禁止外部调用（除 EntryPoint 外）| 防止验证和执行的 Gas 计算出现差异                           |
| `userOpHash` 必须唯一且不可重放 | 每个 UserOp 只能被执行一次；nonce 和签名确保唯一性              |

## 应用领域

### 在钱包（MetaMask）中的应用

MetaMask 的智能账户功能基于 ERC-4337：

- 用户创建或升级为智能账户（通过 EIP-7702 升级现有 EOA）
- 支持 Passkey 签名（手机生物识别）
- 支持批量交易（一次确认完成 approve + swap）
- Paymaster 代付 Gas（DApp 赞助新用户的 Gas 费）

### 基础设施生态

| 组件        | 代表项目                              | 说明                        |
| ----------- | ------------------------------------- | --------------------------- |
| Bundler     | Alchemy, Pimlico, Stackup            | 接收 UserOp 并打包上链      |
| Paymaster   | Pimlico, Biconomy                    | 代付 Gas 服务                |
| 智能账户    | ZeroDev, Biconomy, Safe{Core}        | 可定制的智能账户实现         |
| 签名方案    | WebAuthn, Passkey, ECDSA             | 各种身份验证方式             |

## 与其他标准的关系

| 相关标准    | 关系类型   | 说明                                                      |
| ----------- | ---------- | --------------------------------------------------------- |
| **EIP-712**  | 配合使用   | UserOperation 的签名格式通常基于 EIP-712                  |
| **ERC-1271** | 理念延伸   | 账户的签名验证逻辑继承了 ERC-1271 的设计思路              |
| **EIP-7702** | 配合互补   | EIP-7702 让 EOA 升级为 4337 兼容的智能账户（无需迁移资产）|

## 安全考虑

### 1. 验证阶段的限制

`validateUserOp` 中不能使用 `block.timestamp`、`block.number` 等会因区块不同而变化的操作码，否则作恶的 Bundler 可以利用这些差异。

### 2. 签名聚合

多个 UserOp 可以使用 BLS 签名聚合，大幅降低链上验证成本。但聚合器的设计必须防止 DoS 攻击（一个无效签名导致整批失败）。

### 3. Paymaster 代付的审查风险

如果 Paymaster 拒绝为特定账户代付，该账户的 UserOp 可能无法被打包。用户应始终确保自己有 ETH 储备用于支付 Gas（作为后备）。

### 4. 账户升级风险

可升级的智能账户合约如果升级逻辑有漏洞，可能被恶意升级接管所有资产。建议使用多签或时间锁控制升级权限。

### 你不用写的 ✅

| 组件 | 谁写的 | 你干什么 |
|---|---|---|
| **EntryPoint** | eth-infinitism 官方 | 直接用已部署的合约地址 |
| **Bundler** | Alchemy / Pimlico / Stackup | 调用它们的 API，或自己跑一个 bundler 节点 |
| **UserOperation 结构体** | ERC-4337 标准定义 | import 标准库即可 |
| **内存池（mempool）** | Bundler 自带 | 无需关心 |
| **签名工具库** | OpenZeppelin（ECDSA、EIP712） | import 直接用 |

### 实际项目结构

```
一个最简可用的 4337 项目：

项目源码：
├── MySmartAccount.sol      ← ✍️ 你写：实现 IAccount
├── MyPaymaster.sol          ← ✍️ 你写（可选）：实现 IPaymaster
├── MyAccountFactory.sol     ← ✍️ 你写：CREATE2 部署智能账户
│
依赖（全部引用现成的）：
├── @eth-infinitism/account-abstraction  ← EntryPoint + 接口定义
├── @openzeppelin/contracts              ← ECDSA、EIP712、ERC20……
└── bundler API                          ← Alchemy/Pimlico 等第三方服务
```

**核心就一个函数** —— `validateUserOp()`。你在里面写什么验证逻辑，你的智能账户就有什么能力。余下的基础设施（EntryPoint、Bundler、mempool）全是别人搭好的，你只需要引用。
